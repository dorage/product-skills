# 스펙 포맷

문서를 쓰는 모든 단계(`product:draft`·`product:persona-review`·`product:design`·`product:flow`·`product:task`·`product:brief`·`product:quick`·`product:bdd`)가 함께 따르는 공용 포맷이다. 결정·마커·답 반영·저장 위치·윤문의 모양은 이 문서 한 곳에 있다.

단계마다 결과물 모양(절 구성, 템플릿, 단계 전용 표기, 완성 조건)은 `references/{스킬 이름}.md` 에 있다. brief 스킬은 `references/brief-format.md` 를 쓴다. 단계 문서가 이 문서의 일부를 따르지 않으면, 단계 문서 맨 위에 예외를 적는다.

## 한 번만 쓴다

스펙은 자연어라서, 같은 내용이 두 곳에 있으면 한쪽만 고쳐지고 문서 안에서 서로 어긋난다.

- 규칙, 수치, 용어 정의, 결정 답은 스펙 전체에서 한 곳에만 쓴다
- 다른 곳에서는 다시 쓰지 않고 가리킨다: 결정은 ID(`A1`), 요구사항은 번호(`요구사항 3`), 용어는 용어 이름
- 요약·결론 블록을 따로 두지 않는다. 요약은 본문을 다시 쓴 것이라 답이 오면 바로 어긋난다
- 예시 숫자는 그 예시가 있는 자리 하나에만 둔다. 그림이 있으면 그림이 그 자리이고, 그림 아래 글은 읽는 법만 적는다
- 고칠 때는 고친 내용이 다른 곳에 또 있는지 검색해, 있으면 한 곳만 남기고 나머지는 가리키게 바꾼다

## 필요한 결정

마스터가 답해야 할 것과 이미 답한 것을 모은다. 결정 하나는 문서에 한 번만 나온다.

### 열린 결정

- 다른 결정이 이 답에 따라 달라지는 것부터 위에 둔다
- 그룹 문자로 묶는다 (예: A 할인 규칙, B 가입·인증, C 정산). 그룹마다 5개 이하
- 그룹 문자는 문서마다 쓰는 범위가 다르다. 한 기능의 결정 ID 가 두 문서에서 겹치지 않게 하기 위해서다
    - 요구사항(`product:draft`, `product:quick` 의 요구사항): `A`~`H`
    - 화면흐름(`product:flow`): `M`~`R`
    - 설계(`product:design`, `product:quick` 의 설계 절): `S`~`Z`
- 범위 안의 글자가 모자라면 글자를 더 쓰지 않는다. 기능을 더 작게 나누자고 마스터에게 권한다. 나눌 경계(요구사항 번호 묶음)를 함께 적는다. 결정이 이만큼 많으면 한 문서로 다루기에 기능이 크다는 뜻이기 때문이다
- 결정마다
    - `**A1. {무엇을 정하는가}**` 한 문장
    - 구체 예시: 옵션마다 결과가 어떻게 달라지는지 숫자로 (예: 한도 1,500원, 라떼 2잔 → 잔마다 3,000원, 줄마다 1,500원)
    - 옵션 a/b/c 와 트레이드오프 한 줄씩. 마스터가 "A1. a" 로 답할 수 있게 한다
    - 추천안: `@초안 a안 — {근거}`
    - LLM 이 알 수 없는 것(가격 정책, 계약 조건, 외부 합의)은 추천 없이 `@미정 — {이유 한 줄}`
    - 걸린 자리: `걸린 곳: 요구사항 2, 요구사항 5`

### 정해진 결정

답을 받은 결정은 「열린 결정」에서 지우고 정해진 결정으로 옮긴다. 복사하지 않는다. 결정마다 아래를 담고, 늘어놓는 모양(불릿, 표)은 단계 문서가 정한다.

- ID 와 무엇을 정했는가 한 문장
- 답: `@확정 ({YYYY-MM-DD} "{답 원문}")`. 짧은 답을 풀어 썼으면 `@해석` 과 풀어 쓴 뜻
- 답한 사람: 「저장 위치」「product 폴더 찾기」의 `mode` 가 `internal` 이면, 문서에 적는 답 원문 뒤에 ` — {이름}` 을 붙인다 (예: `@확정 (2026-11-22 "a" — 홍길동)`). 내부 셋업 문서는 여러 사람이 답하기 때문이다. 외부 셋업이면 붙이지 않는다
    - `{이름}`: 기능 폴더에서 `git config user.name` 을 실행한 결과
    - 결과가 비면 `이름 없음` 을 붙이고, 끝맺음에 "`git config --global user.name "{이름}"` 을 실행하면 다음 답부터 이름이 붙습니다" 한 줄을 붙인다
- 반영한 곳: `요구사항 2 인수 조건 1, 요구사항 5 업무 규칙`. 반영한 규칙 내용은 여기에 다시 쓰지 않는다
- 옵션, 예시, 추천 근거는 지운다. 정해진 뒤에는 다시 읽을 일이 없다

### 명세화

불명확한 프로퍼티는 「열린 결정」에 올린다.

- 날짜 윈도우 요구사항 → 구체 날짜 예시로 포함/미포함 확인
- 수치 윈도우 요구사항 → 최소/최대/이상/이하/초과/미만 확인
- 화폐/대사/정산/결제 → 소숫점 정확도 확인
- 숫자 연산 → 소숫점 정확도 확인

## 마커

모든 인수 조건, 업무 규칙 행, 원칙 문장에 마커 하나를 붙인다.

- **MUST**: 스펙, PR 본문, 결정이 필요한 답변에 마커를 붙힌다.
- **MUST NOT**: 그 외 문서(README, 가이드, 회의록 등)에는 붙이지 않는다.

```
- @결정: 마스터가 스펙/SSOT에 적은 결정을 그대로 옮긴 것입니다.
- @해석: 마스터가 정하긴 했지만 결정 문장이 짧아서, LLM이 뜻을 풀어 쓴 것입니다. 풀어 쓴 내용이 마스터의 뜻과 맞는지 확인이 필요합니다.
- @초안: 마스터의 결정 문장이 아예 없습니다. 근처에서 내려진 결정 때문에 빈 곳이 드러났고, LLM이 그 빈 곳을 새 규칙으로 채웠습니다. 세 표기 가운데 틀릴 가능성이 가장 큽니다.
- @미정: LLM이 초안을 쓸 수 없는 빈 곳입니다. 가격 정책, 외부 계약처럼 LLM이 알 수 없는 정보가 필요할 때만 씁니다. 초안을 쓸 수 없는 이유를 한 줄 붙입니다. 초안을 쓸 수 있으면 @초안으로 씁니다.
---
- @사실: 코드 경로, 실행 결과, 공식 문서로 LLM이 직접 확인한 사실입니다. 출처를 같이 적습니다. 이번 작업에서 직접 확인한 것만 해당합니다. 이전 산출물에서 옮긴 값("N건 미반영", "N일째" 같은 카운트 포함)은 다시 확인하기 전까지 @가정 입니다.
- @가정: 확인하지 않은 채 참이라고 둔 사실입니다. 틀리면 그 위에 세운 결론이 함께 무너집니다. @가정 위에서 진행할 때는 분기형 문장("X 조건이면 A, Y 조건이면 B")으로 씁니다.
---
- @확정: @해석, @초안, @미정 이 마스터의 답변으로 정해진 것입니다. 마스터 답변 인용과 날짜를 같이 적습니다. 마스터의 짧은 답을 LLM이 풀어 쓴 것은 @확정 이 아니라 @해석 입니다(비대칭, 조건부, 맥락 의존 가능성 점검).
```

@확정 의 답변 인용은 「정해진 결정」의 그 ID 자리에 한 번만 쓰고, 다른 자리는 `@확정 (A2, {YYYY-MM-DD})` 처럼 ID 로 가리킨다.

해석이 3개 이상 얽혀야 스펙을 쓸 수 있으면, 쓰기 전에 그 해석들을 마스터에게 먼저 확인받는다.

## 답 반영

마스터가 "A1. 임직원 할인 = 제휴회사", "B4. A안", "C3. C2" 처럼 답하면 이렇게 고친다.

- 결정 ID 로 스펙을 검색해, 그 결정에 걸린 인수 조건·업무 규칙·그림을 모두 고친다
- 고친 자리의 마커를 `@확정 (A2, {YYYY-MM-DD})` 로 바꾼다. 답 원문은 「정해진 결정」의 그 ID 자리 한 곳에만 둔다
- "C2" 처럼 다른 답을 가리키거나 짧은 답을 풀어 쓴 것은 @확정 이 아니라 @해석 이다
- 그 결정을 「열린 결정」에서 「정해진 결정」으로 옮긴다
- 답 때문에 임시 이름이 확정되면 스펙 전체에서 임시 이름을 바꾸고, 남지 않았는지 검색한다
- 답 때문에 새로 생긴 빈 곳은 다음 번호로 「열린 결정」에 추가한다 (예: A6, A7)

## 저장 위치

`product:draft`·`product:quick`·`product:persona-review`·`product:design`·`product:flow`·`product:brief`·`product:task`·`product:bdd` 가 문서를 쓰는 자리다. 문서는 `/product:setup` 으로 셋업한 product 폴더(`.product/`) 안 기능 폴더에 모은다. 어느 폴더에서 스킬을 불러도 위로 가장 가까운 product 폴더 한 곳에 한 기능의 문서가 쌓이게 하려는 것이다.

product 폴더 이름은 설정 파일(`.product-settings`)의 `productDirName` 으로 바꿀 수 있다. 없으면 `.product` 다. 스킬은 이름을 짐작하지 않고 아래 명령이 돌려준 `productDir` 만 쓴다. 아래 예시의 `.product/` 도 그 자리에 `productDir` 이 들어간다.

### product 폴더 찾기

문서를 쓰기 전에 아래 명령을 그대로 실행한다. 경로를 받았을 때도 실행한다(「폴더 고르기」).

```bash
if command -v product >/dev/null 2>&1; then
  product root --json --expect "$(cat {플러그인 폴더}/cli-version)"; echo "EXIT $?"
else
  echo "NO_CLI"
fi
```

- `{플러그인 폴더}`: 이 문서가 든 `references/` 의 위 폴더. 스킬이 이 문서를 읽을 때 쓴 `${CLAUDE_PLUGIN_ROOT}` 경로다
- 경로를 받았으면 `product root` 뒤에 `--from {경로}` 를 붙인다. 아직 없는 파일 경로여도 된다

결과는 아래로 가른다. `EXIT` 가 0 이 아니면 문서를 쓰지 않는다. 경로를 받은 갈래의 `EXIT 4` 만 예외다(「폴더 고르기」). 표준 출력의 JSON 은 실패해도 남는다.

- `EXIT 0`: JSON 의 `productDir`(product 폴더), `mode`(`external` 외부 셋업, `internal` 내부 셋업), `legacyDir`(예전 보관 폴더 `~/.sdd/{리포 이름}/` 이 있으면 그 경로, 없으면 `null`)를 쓴다. `--from` 이면 `inRepos` 도 온다. `--from` 으로 찾은 곳에 product 폴더가 없으면 `productDir`·`mode` 가 `null` 이다
- `NO_CLI`: "product CLI 가 없습니다. node 를 설치한 뒤 `/product:setup` 을 다시 부르세요" 한 줄
- `EXIT 3`: "product 폴더가 없습니다. `/product:setup` 을 먼저 부르세요" 한 줄
- `EXIT 4`: JSON `reason` 의 파일 경로와 문제를 한 줄로 보여 주고 "`/product:setup` 을 다시 부르세요" 한 줄
- `EXIT 5`: "product CLI 가 플러그인이 기대하는 버전보다 낮습니다. `/product:setup` 을 다시 부르세요" 한 줄
- 그 밖: JSON `reason` 한 줄

### 기능 폴더

- `{productDir}/features/{yymmdd}_{feature_summary}/` 한 폴더에 한 요청의 `requirements.md`·`design.md`·`flow.md`·`brief.md`·`tasks.md`·`scenarios.md`·`features/` 를 모은다
    - 예: `.product/features/261102_partner-cafe-staff-discount/requirements.md`
- `{yymmdd}`: 폴더를 만드는 날의 로컬 날짜 6자리 (예: 2026-11-02 → `261102`)
- `{feature_summary}`: 설명을 영어 kebab-case 로 줄인 이름. 원문을 옮기지 않고 핵심 명사 위주로 줄인다
    - 영어 소문자·숫자·`-` 만 쓴다. 50자 이내
    - 예: "제휴 카페에서 임직원이 라떼 사면 할인해주는 기능 만들어줘" → `partner-cafe-staff-discount`
- 같은 이름의 폴더가 이미 있으면 끝에 `-2`, `-3` 을 붙인다 (예: `261102_partner-cafe-staff-discount-2`)
- 예전 `{YYYYmmddHHMMSS}_{한국어 요청내용}` 폴더는 이름을 바꾸지 않는다. 경로를 주면 이어 쓴다
- 폴더에 브랜치 이름을 적지 않는다. 한 스펙이 여러 실행 계획과 브랜치로 나뉘기 때문이다

### 폴더 고르기

- 설명에 경로가 있다 → product 폴더를 찾지 않고 그 경로에 쓴다. 폴더면 그 안의 각 스킬 파일
    - 「product 폴더 찾기」를 `--from {경로}` 로 실행해 `mode` 만 읽는다. `mode` 가 `null` 이면 외부 셋업으로 본다
    - `EXIT 4` 면 JSON `reason` 한 줄을 남기고 외부 셋업으로 보고 그 경로에 쓴다. 경로를 주는 것은 product 폴더 찾기가 틀릴 때 쓰는 비상 탈출구라서다. `NO_CLI`·`EXIT 5` 면 쓰지 않는다
    - `inRepos` 가 리포 이름이면 쓰기 전에 "{경로}는 실제 리포 `repos/{inRepos}/` 안이라 리포지토리 관리자에게 보일 수 있습니다" 한 줄을 남기고 그대로 쓴다
- 없으면
    - `product:draft`·`product:quick` → `{productDir}/features/` 아래에 새 기능 폴더를 만든다. 둘 다 한 기능의 첫 문서를 쓰기 때문이다. `features/` 가 없으면 함께 만든다
    - `product:persona-review`·`product:design`·`product:flow`·`product:brief`·`product:task`·`product:bdd` → `{productDir}/features/` 의 폴더를 최대 4개로 `AskUserQuestion` 한 번에 보여 주고 고르게 한다. 아래 명령의 순서대로 보여 주고, 첫 옵션이 가장 최근 폴더다
        - 폴더가 하나도 없으면 쓰지 않고 "`/product:draft` 를 먼저 실행하세요" 한 줄을 남긴다
    - `legacyDir` 가 `null` 이 아니면 고르게 할 때(폴더가 없다는 줄을 남길 때도) "예전 기능은 `{legacyDir}` 에 있습니다. 경로를 주면 이어 씁니다" 한 줄을 함께 남긴다. 예전 보관 폴더 안의 파일은 옮기거나 지우지 않는다

```bash
d=$(find "{productDir}/features" -mindepth 1 -maxdepth 1 -type d ! -name '.*' -exec basename {} \; 2>/dev/null)
{ printf '%s\n' "$d" | grep -E '^[0-9]{6}_' | sort -r; printf '%s\n' "$d" | grep -vE '^[0-9]{6}_' | grep . | sort; } | head -n 4
```

이름 앞 6자리 날짜의 내림차순이 최근 순서다. 같은 날의 폴더끼리는 이름의 역순이다. 이름이 6자리 날짜와 `_` 로 시작하지 않는 폴더(예전 14자리 시각 폴더 포함)는 맨 뒤에 놓는다.

- 쓰기 전에 채팅에 "{경로}에 씁니다" 한 줄을 남긴다. 경로가 정해지기 전에는 파일을 쓰지 않는다
- 같은 파일이 이미 있으면 덮어쓰기 전에 읽고, 갱신인지 새 파일인지 한 번 묻는다

### 내부 셋업 문서에 쓰지 않을 것

「product 폴더 찾기」의 `mode` 가 `internal` 이면 문서는 리포에 커밋되어 product 를 설치하지 않은 팀원도 읽는다. 아래는 문서에 쓰지 않고 채팅에만 남긴다.

- 개인 설정: 사용자 전역 지시(`~/.claude/` 아래 파일), 설치한 플러그인과 스킬, 개인 git 설정
- 이 컴퓨터에서 확인한 사실: 홈 폴더 아래 경로, 이 컴퓨터에 깔린 도구와 버전, 리포 밖 폴더를 본 결과

리포 안 코드 경로와 리포 안에서 돌린 명령 결과는 팀원도 다시 확인할 수 있어서 문서에 써도 된다.

## 윤문

문서를 다 쓴 뒤 `humanize-korean@im-not-ai` 플러그인으로 문장을 사람이 쓴 글처럼 다듬는다. 플러그인 설치는 `product:setup` 이 맡는다. 다듬는 것은 문장뿐이고, 내용과 구조는 그대로 둔다.

### 대상과 때

- 대상: `requirements.md`·`design.md`·`flow.md`·`tasks.md`
- 거치지 않는 것: `brief.md`(입력의 문장을 한 글자도 바꾸지 않는 사본이다. `product:brief` 는 원본 `requirements.md` 가 윤문을 거치지 않았을 때 원본을 윤문한 뒤 쓴다. `references/brief-format.md` 「내용은 바꾸지 않는다」), `features/*.feature`·`scenarios.md`(Gherkin 키워드와 단계 문장이 깨진다), 공유 문서 경로(로컬 파일이 아니다)
- 때: 스킬이 파일을 다 쓰고 자기 검증(`(작성 중)` 검색, 마커·구조 검증)을 마친 직후. 「답 반영」으로 고친 뒤와 `product:persona-review` 가 고친 뒤에도 다시 거친다
- 플러그인이 없으면(`claude plugin list` 에 `humanize-korean@im-not-ai` 가 없으면) 건너뛰고, 끝맺음에 "윤문을 건너뛰었습니다. `/product:setup` 을 실행하세요" 한 줄을 붙인다. 문서 작성은 막지 않는다

### 부르는 법

- `cd {기능 폴더}` 로 기능 폴더로 옮겨 간다. humanize-korean 은 지금 폴더 아래에 작업 파일을 만들기 때문에, 작업 파일이 product 폴더 안에만 생기게 하려는 것이다
- `cp {파일} {기능 폴더}/.{파일 이름}.before` 로 원본을 남긴다
- `Skill(skill="humanize-korean:humanize-korean")` 를 부르고, args 에 아래를 넘긴다
    - 입력 파일 경로
    - 강도 "가볍게". 스펙은 고칠 곳이 적은 글이라 과윤문을 막는 가벼운 경로가 맞다
    - 장르 `report`
    - 건드리지 않을 것: 헤딩 줄, `@` 마커와 괄호 속 출처, 결정 ID(`A1`·`S2`)와 요구사항 번호, EARS 키워드(`THE System`·`SHALL`·`WHEN`·`WHILE`·`IF`·`THEN`), 표의 행과 열, 코드 블록과 mermaid, 백틱 안 글자, 경로, 숫자와 날짜, 체크박스
- humanize-korean 이 `Agent` 로 부르는 에이전트(`humanize-korean:humanize-monolith`·`humanize-diagnostician`·`humanize-finalizer`)는 모두 `model: "sonnet"`, `effort: "low"` 를 넘겨 부른다. 에이전트 정의의 모델 대신 이 값을 쓴다. 문장만 다듬는 가벼운 일이라 sonnet low 로 충분하고, haiku 는 이 계정에서 꺼 두었다
- 결과 `final.md` 에서 요약 블록과 끝의 빈 줄을 지운다. 이 명령으로 `final.md` 자체를 고친다. `{작업 폴더}` 는 「작업 폴더 치우기」에서 `_workspace/{run_id}/` 를 찾은 폴더다
    - `perl -0pi -e 's/\n*<!-- HUMANIZE-SUMMARY.*?-->\s*/\n/s' {작업 폴더}/_workspace/{run_id}/final.md`

### 덮어쓰기 전 검사

윤문본이 지켜야 할 것을 원본과 윤문본에서 뽑아 비교한다. 같을 때만 덮어쓴다.

```bash
keep() {
  grep -E '^#' "$1"
  awk '/^```/{f=!f; print; next} f' "$1"
  grep -c '^|' "$1"
  grep -oE '@(결정|해석|초안|미정|사실|가정|확정)|[A-Z][0-9]+|[0-9][0-9,.:+-]*|`[^`]+`|THE System|SHALL|WHEN|WHILE|IF|THEN' "$1" | sort
}
diff <(keep {원본}) <(keep {윤문본}) && echo SAME || echo DIFF
```

- `SAME`: 윤문본으로 원래 파일을 덮어쓰고 `.{파일 이름}.before` 를 지운다
- `DIFF`: 원래 파일을 그대로 두고, 끝맺음에 "윤문이 {diff 첫 줄}을 바꿔서 원본을 유지했습니다" 한 줄을 붙인다

### 작업 폴더 치우기

humanize-korean 은 지금 폴더 아래 `_workspace/{run_id}/` 에 작업 파일을 남긴다. `cd` 가 다음 명령까지 이어지지 않으면 세션 폴더(Claude Code 를 연 폴더)에 생긴다. 리포를 더럽히지 않도록 끝나면 기능 폴더로 모은다.

- `{작업 폴더}`: `{기능 폴더}/_workspace/{run_id}/` 가 있으면 기능 폴더, 없으면 세션 폴더다. 두 곳 다 없으면 옮기지 않고 끝맺음에 "윤문 작업 파일을 찾지 못했습니다" 한 줄을 붙인다
- `mv {작업 폴더}/_workspace/{run_id} {기능 폴더}/_humanize/{run_id}` 로 옮긴다. `01_input.txt` 가 윤문 전 원문으로 남는다
- `{작업 폴더}/_workspace/` 가 비었으면 `rmdir {작업 폴더}/_workspace` 로 지운다. 다른 run 이 남아 있으면 그대로 둔다
- 「부르는 법」에서 옮겨 간 지금 폴더가 남아 있을 수 있으니 `cd {세션 폴더}` 로 돌아온다
