# 착수 인수인계 문서 (kickstart.md)

`product:kickstart` 가 쓰는 인수인계 문서의 모양과, 그 문서를 받은 지휘 세션이 따르는 역할 규칙이다. `references/spec-format.md` 에서 따르지 않는 것은 아래와 같다.

- 결정과 마커를 두지 않는다. 결정은 요구사항·설계 문서에 있다
- 윤문을 거치지 않는다. 마스터의 원문 인용이 바뀌면 안 되기 때문이다
- 머리말 줄(spec-format 「문서 머리말」)을 두지 않는다. 제목 아래는 「읽을 문서」다
- 커밋하지 않는다. 세션 사이 메모이고 작업 결과물이 아니다

## 기준

지휘 세션에 있는 것은 이 문서와 문서가 가리키는 세 문서뿐이다. 넘기는 세션이 채팅에서 듣고 정하고 돌려 본 것은 이 문서에 적히지 않으면 사라진다.

- 판정: 아무 맥락 없는 세션이 이 문서와 세 문서만 보고 질문 없이 첫 작업을 서브에이전트에 지시할 수 있는가
- 해당 없는 절은 지우지 않고 "없음" 을 적는다. 절이 빈 것과 절이 없는 것은 읽는 세션에게 뜻이 다르다

## 한 번만 쓴다 (네 문서 사이)

- 요구사항·설계·구현 계획 문서에 있는 규칙·수치·인터페이스·작업 절차를 옮겨 적지 않는다. `references/task.md` 「한 번만 쓴다 (세 문서 사이)」의 가리키는 법을 쓰고, 작업은 `T1` 처럼 ID 로 가리킨다
- kickstart.md 에만 있는 것: 지휘 세션의 역할, 넘기는 세션의 맥락, 진행 기록
- 진행 상태(어느 작업이 끝났는가)는 tasks.md 의 DAG 한 곳에만 둔다. kickstart.md 「진행 기록」에는 DAG 에 담기지 않는 것만 적는다

## 문서 구성 (이 순서)

### 제목과 읽을 문서

- 제목: `# {기능} 착수 인수인계`. 기능 이름은 요구사항 문서 제목에서 가져온다
- 「읽을 문서」: 세 문서의 절대경로. 기능 폴더가 지휘 세션이 뜨는 폴더 밖에 있을 수 있어서 절대경로로 적는다

### 역할

「역할 규칙」의 인용 블록을 그대로 둔다. 고쳐 쓰지 않는다.

### 완수조건

- 기본: tasks.md 의 모든 작업이 `done` 이고, 작업마다 「완료 확인」이 통과했다
- 마스터가 범위를 줄였으면(예: "T3 까지만") 그 범위를 원문과 함께 적는다

### 시작할 작업

tasks.md 에서 선행이 모두 `done` 인 `todo` 작업 ID 목록. 이름과 절차는 옮겨 적지 않는다.

### 세션에서 넘기는 맥락

네 소절을 모두 둔다.

- 「마스터의 제약과 지시」: 채팅에서 나온 문장을 원문 그대로 인용한다. 요약하지 않는다
- 「문서에 없는 결정과 버린 대안」: 세 문서에 반영되지 않은 결정, 버린 대안, 버린 이유. 이유가 없으면 지휘 세션이 같은 갈림길에서 같은 고민을 다시 한다
- 「실측한 것」: 직접 돌려 본 명령과 결과. 실패한 시도를 포함한다
- 「확인 필요」: 확정하지 못한 것과 확인하는 방법. 요구사항·설계 문서에 열린 결정이 남았으면 결정 ID

`mode` 가 `internal` 이어도 이 문서는 커밋하지 않으므로 spec-format 「내부 셋업 문서에 쓰지 않을 것」을 따르지 않아도 된다.

### 진행 기록

넘기는 세션은 "없음" 으로 둔다. 지휘 세션이 쓴다. 작업을 검수할 때마다 DAG 에 담기지 않는 것만 한 줄씩 더한다.

- 작업 ID, 커밋, 검수에서 되돌려 보낸 횟수와 이유
- 계획과 다르게 한 것과 그 이유
- 범위 밖에서 발견한 문제. 고치지 않고 적기만 한다

### 세션

- 넘긴 세션 ID. 알 수 없으면 "확인하지 않았다"
- 다시 넘겨 쓴 문서면, 앞서 넘긴 세션 ID 를 지우지 않고 아래에 더한다

### 요청 원문

kickstart 를 부른 마스터의 문장을 그대로 인용한다.

## 형식

````markdown
# {기능} 착수 인수인계

## 읽을 문서

- 요구사항: `{절대경로}/requirements.md`
- 설계: `{절대경로}/design.md`
- 구현 계획: `{절대경로}/tasks.md`

## 역할

> 이 문서를 받은 세션은 지휘 세션이다. 지시와 검수만 한다.
>
> - 직접 하는 것: 문서와 코드 읽기, 서브에이전트에 작업 지시, 서브에이전트가 만든 변경 읽기, 작업의 「완료 확인」 명령 실행, tasks.md 진행 표시, 이 문서 「진행 기록」 쓰기, 마스터에게 질문
> - 서브에이전트에 맡기는 것: 코드와 테스트 수정, 브랜치·워크트리·PR 준비, 커밋과 푸시, 원인 조사처럼 여러 파일을 읽어야 하는 일
> - 작업 하나에 서브에이전트 하나를 쓴다. 지시에는 작업 ID, 세 문서의 절대경로, 그 작업의 「가리키는 곳」, 이 문서에서 그 작업에 걸리는 맥락을 넣는다. 서브에이전트는 이 문서를 보지 못한다
> - 서브에이전트에게 tasks.md 의 진행 표시를 고치지 말고, `kickstart.md` 를 커밋에 넣지 말라고 지시한다
> - 검수는 서브에이전트의 보고가 아니라 실제 변경과 「완료 확인」 명령의 결과로 한다. 통과하지 못하면 이유를 붙여 같은 작업을 다시 지시한다. 직접 고치지 않는다
> - 검수를 통과한 작업만 tasks.md 「진행 규칙」대로 표시한다. 표시하는 곳은 「읽을 문서」에 적힌 경로의 tasks.md 다. tasks.md 가 리포 안에서 커밋되는 파일이면, 표시한 뒤 그 변경의 커밋을 서브에이전트에 맡긴다
> - 한 번에 작업 하나를 진행한다. 화살표로 이어지지 않은 작업을 동시에 진행하려면 「바꿀 파일」이 겹치지 않아야 하고, 서브에이전트마다 따로 떨어진 워크트리에서 하게 한다
> - 설계의 빈 곳을 만나면 메우지 않는다. 마스터에게 `design.md` 에 올릴 결정 문장으로 묻고, 그 답에 걸리지 않는 작업을 먼저 진행한다
> - 컨텍스트가 차면 `/product:kickstart {기능 폴더}` 를 불러 다음 세션에 넘긴다

## 완수조건

- tasks.md 의 모든 작업이 `done` 이고, 작업마다 「완료 확인」이 통과했다
````

## 역할 규칙

「형식」의 「역할」 인용 블록이 이 규칙이다. kickstart.md 를 받은 지휘 세션이 따른다.

- 지휘 세션이 코드를 직접 고치지 않는 이유: 구현의 세부가 지휘 세션의 컨텍스트를 채우면, 계획 전체를 보고 검수하는 자리가 줄어든다
- 서브에이전트의 모델은 정하지 않는다. 지휘 세션이 뜬 환경의 설정과 지시를 따른다
- 지휘 세션이 문서를 고치는 곳은 두 곳뿐이다: tasks.md 의 진행 표시(DAG 의 `class` 줄과 체크박스), kickstart.md 「진행 기록」
