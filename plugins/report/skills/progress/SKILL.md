# 진행 보고서 만들기

커밋과 PR 본문을 근거로, 개발자가 아닌 사람도 첫 두 쪽과 하이라이트만 읽고 "어디까지 왔고 무엇이 되었고 다음은 무엇인가"를 아는 16:9 PDF 를 만든다.

## 적용하는 원칙

원칙의 내용은 `${CLAUDE_PLUGIN_ROOT}/principles/` 의 문서에만 있다. 일을 시작하기 전에 아래 문서를 모두 읽고, 이 문서에는 원칙의 내용을 다시 쓰지 않는다.

이 문서의 `${CLAUDE_PLUGIN_ROOT}` 가 경로로 바뀌지 않고 글자 그대로 보이면, 이 스킬 폴더(`SKILL.md` 가 든 폴더)의 두 단계 위 폴더 경로로 바꿔 넣는다. 아래 템플릿과 스크립트 경로도 같다.

## 착수 전 확인

아래 중 설명에서 알 수 없는 것만 한 번에 묻는다. 알 수 있는 것은 묻지 않고 뼈대에 적어 보여 준다.

- 범위: 기간(시작일, 끝일) 또는 기능(PR 번호, 브랜치, product 기능 폴더). "이번 주"는 이번 주 월요일부터 오늘까지로 풀어 뼈대에 날짜로 적는다
- 리포: 어느 폴더의 리포들인가. 기본은 지금 폴더(리포가 아니면 바로 아래 리포들)
- 작성자: 누구의 커밋인가. 기본은 `git config user.name` 과 `user.email` 의 아이디
- 읽는 사람과 목적: 누가 읽고 무엇을 확인하려는가. 개발자가 아닌 윗선이면 `readers-words.md` 를 엄격히 적용한다
- 마스터만 보는 메모가 필요한가

## 자료 모으기

```bash
# 기간
npx tsx "${CLAUDE_PLUGIN_ROOT}/skills/progress/scripts/collect.ts" {리포 또는 리포들이 든 폴더} --since 2026-11-23 [--until 2026-11-27] [--author "아이디|이름"]
# 기능 (브랜치)
npx tsx "${CLAUDE_PLUGIN_ROOT}/skills/progress/scripts/collect.ts" {리포} --range origin/main..origin/{브랜치} [--author ...]
```

- 스크립트는 리포마다 범위 안 커밋, 같은 제목을 뺀 수(다른 브랜치로 옮긴 같은 커밋), 커밋이 든 원격 브랜치와 그 브랜치의 PR, 브랜치로 못 찾은 PR(커밋 SHA 로 검색)을 뽑는다. 폴더 안에 `repos/` 가 있으면(product 외부 셋업) 그 안의 리포를 쓴다. `tsx` 를 받을 수 없으면 `node` 로 돌린다 (Node 24 이상)
- 머지 커밋으로만 들어온 PR(여러 작업을 하나로 합친 PR)은 스크립트가 못 찾는다. 기간 범위면 `gh pr list --author @me --state merged --search "merged:>={시작일}"` 로 한 번 더 찾는다
- 기능 범위를 PR 번호로 받았으면 스크립트 없이 그 PR 들을 바로 읽는다
- 찾은 PR 은 모두 본문까지 읽는다: `gh pr view {번호} --json title,body,state,mergedAt,additions,deletions`. 지표는 대부분 PR 본문에 있다
    - 작업 목록 체크박스 → 계획 대비 완료
    - 검증·테스트 항목 → 통과한 검사 수. 어디서 돌린 결과인지(공용 자동 검사인지 담당자 컴퓨터인지) 함께 적는다
    - 비용·시간 추정 → 줄어든 값. `label-estimates.md` 대로 추정이라고 적는다
    - 배포 순서·남은 일 → 다음 액션과 출시 단계
- product 기능 폴더(`requirements.md`, `tasks.md`)가 있으면 `tasks.md` 맨 위 mermaid 의 `class … done` 줄과 `class … todo` 줄에 든 작업 ID 수를 계획 대비 완료로 쓰고, `requirements.md` 의 목적을 배경으로 쓴다
- 커밋 수와 날짜별 건수는 자료가 빠지지 않았는지 보는 데만 쓴다. 보고서 지표로 쓰지 않는다

PR 에 묶이지 않은 커밋은 제목끼리 묶어 "작업 묶음"을 직접 만들고, 뼈대의 "LLM 이 채운 문장"에 그렇게 묶었다고 적는다.

## 뼈대 먼저

파일을 만들기 전에 아래를 채팅으로 보여 주고 승인을 받는다. 뼈대의 문장은 보여 주기 전에 `polish-without-mark.md` 대로 윤문한다. 하이라이트 문장은 이 표에 적힌 것이 전부다.

| 쪽 | 층 | 하이라이트 문장 | 아래에 두는 세부 | 지표 | 근거 출처 |
| --- | --- | --- | --- | --- | --- |
| 1 | 표지 | … | 범위(날짜 또는 기능), 작성자 역할 | | |
| 2 | 결론 | ① … ② … ③ … | 문장마다 근거 쪽, 계획 대비 진행 막대 | 계획 대비 완료 | |
| 3 | 가. 배경 | … | 흐름 그림 | | PR 번호와 본문 항목 |
| 4 | 가. 성과 | … | 이제 되는 것 표 | 12개 중 12개 | |
| … | | | | | |
| 끝 | 다음 액션 | … | 출시 단계 막대, 남은 일 | 7단계 중 3단계 | |

- 층은 표지, 결론, 묶음(가·나·다), 다음 액션 순서다. 묶음은 결론 문장 하나에 하나다
- 묶음 안은 배경 → 성과 순서다. 한 쪽으로 충분하면 두 칸 견본(왼쪽 배경, 오른쪽 성과)에 담는다
- 쪽마다 지표 칸을 채운다. 셀 수 있는 지표가 없는 쪽은 그 쪽이 필요한지 다시 본다

표 아래에 아래를 이어 적는다.

- **차트 후보**: `chart-shows-signal.md` 대로 넣을 차트(쪽, 모양, 보여 주는 신호, 데이터)와 넣지 않을 차트(이유)를 나눠 적는다
- **자료에 넣을 숫자**: "숫자, 어떻게 구했나(출처·계산식·가정), 쓰는 쪽" 표. 마스터가 확인한 숫자만 넣는다
- **말 바꾸기**: `readers-words.md` 의 "만든 사람의 말 → 읽는 사람의 말" 표
- **넣지 않을 말**: 바꾼 개발 용어, 사람·계정 이름, 서버 주소, 호스트 이름
- **색 세 가지**: 기본은 템플릿 값(배경 `#FFFFFF`, 글자 `#1A1A1A`, 하이라이트 `#4F76C4`)이다. 하이라이트 색은 채도가 높으면 본문보다 튀므로 채도 50% 안팎으로 고른다
- **LLM 이 채운 문장**: 마스터가 말하지 않았고 PR 본문에도 없어서 LLM 이 짐작한 문장(기능의 목적, "다음 주" 같은 시점, 직접 만든 작업 묶음)
- **아직 안 된 것**: 운영 배포 전, 공용 자동 검사 미실행처럼 성과로 오해받을 수 있는 것. 다음 액션 쪽에 넣는다

뼈대를 고쳐 달라는 답이 오면 표 전체를 다시 낸다.

## 만들기

- `${CLAUDE_PLUGIN_ROOT}/skills/progress/assets/template.html` 을 결과물 폴더에 `{보고서 이름}.html` 로 복사한다. 결과물 폴더는 마스터가 정한 곳, 없으면 지금 작업 폴더다. 이름 기본값은 기간이면 `주간 개발 보고 {YYMMDD}`, 기능이면 `{기능 이름} 진행 보고 {YYMMDD}` 다
- 템플릿의 쪽 견본(표지, 결론과 진행 막대, 배경 흐름, 성과 표, 배경·성과 두 칸, 표와 전후 비교 막대, 다음 액션과 출시 단계 막대)을 골라 뼈대 표대로 채운다. 쓰지 않는 견본은 지우고, 쪽 번호(`.pno`)를 다시 매긴다
- 막대 길이는 실제 숫자 비율로 계산해 `width` 또는 `height` 에 넣는다
- 색은 `:root` 의 `--bg`, `--ink`, `--hl` 세 값만 바꾼다. 하이라이트는 `class="hl"` 하나로만 건다

PDF 로 바꾼다.

```bash
"/Applications/Google Chrome.app/Contents/MacOS/Google Chrome" --headless=new --disable-gpu \
  --no-pdf-header-footer --print-to-pdf="$PWD/{보고서 이름}.pdf" "file://$PWD/{보고서 이름}.html"
```

## 검사

report:presentation 의 검사 스크립트를 그대로 쓴다.

```bash
npx tsx "${CLAUDE_PLUGIN_ROOT}/skills/presentation/scripts/check.ts" "{보고서 이름}.html" "{보고서 이름}.pdf" --ban "넣지,않을,말"
```

- `--ban` 에는 뼈대의 "넣지 않을 말"을 모두 넣는다. 바꾼 개발 용어와 `humanize` 도 넣는다
- 스크립트가 못 하는 검사는 직접 한다: 뽑힌 하이라이트만 이어 읽기(배경 → 성과 → 다음 액션으로 이어지는가), 숫자를 PR 본문과 다시 대조하기, PDF 전 쪽을 그림으로 열어 차트와 글자가 넘치지 않는지 보기
- 고친 뒤에는 PDF 를 다시 뽑고 검사 전체를 다시 돌린다

## 마스터만 보는 메모

착수 전 확인에서 필요하다고 한 때만 `{보고서 이름} 메모.md` 로 만든다. 숫자마다 출처를 붙이고, 지표로 쓰지 않은 커밋 수와 날짜별 건수, LLM 이 직접 확인하지 못한 출처를 적는다.

## 공개 범위

로컬 파일로 만든다. 사람 이름, 비용, 서버 정보가 들어가므로 마스터가 요청하기 전에는 온라인 공유 페이지로 올리지 않는다.

## 끝맺음

- 첫 줄: PDF 의 전체 경로와 먼저 볼 쪽
- 검사 결과를 숫자로 적는다 (쪽 수, 색 개수, 쪽별 하이라이트 개수, 넣지 않을 말 건수)
- 뼈대와 달라진 곳이 있으면 전과 후를 나란히 적는다
- 윤문을 했는지 건너뛰었는지 한 줄로 적는다. 자료에는 적지 않는다
- LLM 이 채운 문장과, 직접 확인하지 못한 근거(담당자 컴퓨터에서 돌린 검사, 추정 비용)를 적는다
- 마지막 줄: 마스터가 확인할 것 하나 (예: 다음 액션의 시점이 실제 일정과 맞는가)
